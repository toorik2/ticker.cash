# Red team of v25, 2026-10-25

Scope: `contracts/` (Oracle, Ticker, PriceGated), `node/notary`, `node/daemon` (prover, builder),
`node/core`, and the design record. Assumption: the future the design is built for, with notary rows
run by unrelated operators, permissionless provers and builders racing every minute, mainnet, and
real value (lending, synthetic dollars, escrow) keyed to the price.

Method: one full read of the covenants and the notary/prover/builder code; three independent
reviewers, one per layer, given the code and the assumption but none of the conclusions; proofs of
concept on cashscript's `MockNetworkProvider` (`BCH_2026_05`, libauth token validation) against the
committed artifacts. "Confirmed" means reproduced in the VM harness or traced unambiguously in code
by at least two readers. Nothing was run against the live deployment.

## The weakest links, ranked

### 1. The forgery threshold is four keys, not seven

The covenant takes the lower median of the statements *the builder chose to include*, and any
builder is anyone. With `k = 7` the written price is the fourth-lowest of seven. Four colluding (or
stolen) notary keys plus three honest statements, which are public at every notary's
`/v1/statement`, write any price:

| honest full-set median | written by a 7-row subset with 4 fakes |
|---|---|
| $271.80 | $150.03 |

Reproduced: `Oracle.update` accepts it, 1,701 B, tokens valid. The general rule: with minimum
quorum `q`, `floor((q−1)/2) + 1` fakes own the median. `q = 7 → 4`, `9 → 5`, `11 → 6`, `13 → 7`.
The design record's "≤ 6 liars are absorbed" is true only when all thirteen statements are in the
transaction, which no rule requires and no rule can require (absence is unprovable on chain).

Two variants need no dishonest notary at all:

* **Stablecoin block.** Four rows quote USDT. In a 3 % USDT depeg a builder includes those four and
  the three lowest USD rows and writes a price 3 % high, with every statement genuine.
* **Honest-builder bias.** Even with thirteen honest prices the builder picks any seven and lands
  anywhere between the 4th and 10th order statistic. The honest daemon itself posts as soon as any
  minute has seven statements (`builder.rs`, `build_once`), so in a world of independent provers
  `k` drifts toward 7 and the written price becomes the median of whichever venues answered first.

The seq cannot be forged the same way: every included signature must carry the same `seq`, so a
future minute needs seven keys (see 5).

Mitigations, cheapest first:
* Correct the public claims now (README, docs, plan §5): keys to forge = 4 at `k ≥ 7`.
* `require(k >= 11)`: a one-opcode change, 0 B. Six keys to forge, tolerates two dead rows.
* Put `k` into the commit (`seq ‖ price ‖ k`, 13 B): about +5 B in the Oracle, +1 B per output,
  about +8 B in a consumer that demands `k ≥ 11`. Consumers choose their own bar and the chain
  records how many rows backed each price. Both need a re-genesis.
* Builder policy (no consensus change): wait for all rows or until second ~20 before posting.

### 2. Seven rows share one TLS terminator

The notary validates the certificate chain for the pinned host and signs what that TLS endpoint
returned. Where the exchange sits behind a CDN, the endpoint is the CDN. Public headers on
2026-10-25:

| terminator | rows |
|---|---|
| Cloudflare | Kraken, Coinbase, Crypto.com, Bitfinex, Bitget, OKX, KuCoin (7) |
| CloudFront | Binance, Bybit, HTX (3) |
| own | Gemini, Gate.io (2); Bitstamp unknown |

Cloudflare alone covers seven rows: a quorum at `k = 13`, and far above the four that link 1 needs.
An edge-side change (cache, WAF, a compromised exchange CDN account, a compelled provider) moves
those rows together and the notaries sign it correctly. The registry was chosen for liquidity, not
for terminator diversity, and the trust table in plan §5 does not list this actor.

Mitigations: choose and publish rows by TLS terminator as well as by venue (table change,
re-genesis); optional per-row issuer or fingerprint pin in the notary (code only); MPC mode does not
help here, the edge is the TLS peer in both modes.

### 3. A prover with no keys can stall the oracle and choose its sampling instant

In `ticker-notary` the `(row, seq)` slot is reserved at the hello, before any TLS work, and
`verify_session` has no deadline (tlsn alpha.15 has none either). A prover that sends one valid
hello line and then stays silent holds that row's minute; other provers get `busy`, which the
honest prover treats as failure. Thirteen idle TCP connections per minute stop the oracle.

Worse for integrity: the clock is checked only at the hello. A stalled session can be completed
whenever the prover likes, and the notary signs `seq = m` with a price fetched at `m + Δ` for any
Δ. Stall every row through a move, complete seven at the extreme, post. Every notary is honest and
nothing on chain is wrong. Confirmed by code in `node/notary/src/main.rs` (`handle_session`,
`verify_session`) and `node/daemon/src/prover.rs` (`prove_row`); not reproduced live.

Mitigations, all notary code: a hard session deadline well inside the minute (15–20 s); reserve
the slot on success, not on open, and sign the first session that completes; re-check
`|now − 60·seq| ≤ 90` immediately before signing; cap in-flight sessions per row and per peer
address; bound the hello read as a whole rather than per byte.

### 4. Tickers never die, and an update can also kill them for profit

Three facts, all reproduced in the VM:

* `Ticker.consume()` re-emits the NFT under the same lock, so `this.age` restarts. A holder who
  re-emits once a day keeps a stale price alive forever for a few hundred sats.
* `Ticker.sweep()` constrains only age. A sweeper may keep the immutable NFT, park it in a P2PKH
  token output, and later re-lock it under the Ticker bytecode; a month-old "$500" Ticker is then a
  valid Ticker again. `PriceGated` checks only a static `[minSeq, maxSeq]` window, so any consumer
  that must live longer than its tolerance window (a loan, a synthetic dollar) is exposed to the
  best price its counterparty hoarded.
* The Oracle constrains outputs but never inputs. An update that spends last minute's two Tickers
  as inputs 1 and 2 satisfies `consume()` with its own new Ticker outputs and burns the old NFTs;
  the reserve then loses only the fee. Accepted, 2,224 B, tokens valid. A rational builder will do
  this every minute (it is a 40 % saving on reserve outflow), which makes a Ticker live sixty
  seconds and consumers race the next update for it. Whether that is a feature or a bug is a
  decision the design has not taken.

Also: consume is anyone-can-spend, so a griefer can front-run a consumer's transaction with a
no-op consume of the same Ticker for a few hundred sats per attempt; and before 1-minute blocks
reach mainnet, updates form 10-deep unconfirmed chains per block, so the freshest *confirmed*
Ticker is ten minutes old on average.

Mitigations:
* `sweep()` keyed to the commit's own minute: `require(tx.time >= 60 * int(seq) + LIFETIME)`
  (about 12 B, time-mode locktime, unaffected by Faster Blocks). Re-emission no longer extends
  life; after `LIFETIME` any sweeper destroys it. Make `sweep()` burn (about 7 B).
* Decide the in-update burn: forbid Ticker inputs in `update` (about 20 B) or embrace it and
  document the sixty-second Ticker.
* Replace `PriceGated` as the reference with a two-phase consumer: a claimant posts Ticker A;
  during a CSV window anyone may override with a Ticker B whose `seq` is newer; the newest shown
  settles. Hoarding then helps nobody. Costs a delay and a second transaction, no oracle change.

### 5. Seven keys can brick the head forever, and nothing bounds seq against chain time

`require(int(seq) > int(old))` with a 4-byte `seq`: once a coalition of seven posts
`seq = 0x7fffffff`, no later 4-byte value compares greater (the sign bit makes larger encodings
negative). The head is dead, the reserve stranded, and the only exit is a re-genesis. The same
coalition can lie about the price anyway, but bricking needs no market and leaves no recovery.

Mitigation, about 15 B: `require(tx.time >= 60 * int(seq) - 7200)` in `update`. It compiles to
CHECKLOCKTIMEVERIFY, so the chain enforces median-time-past ≥ locktime ≥ 60·seq − 2 h: a minute
can be at most two hours ahead of chain time. The builder sets a non-final sequence and a locktime
near now. This also stops a clock-skewed coalition.

### 6. No security budget, hot keys, no exclusion, no migration

Notaries earn nothing and are trusted with everything that matters. The signing key is a plain file
on a server that signs every minute, so it is hot by construction; a key holder can sign any
`(seq, price)` at any time (the window and the one-per-minute rule only guard the live session
path, and the statement log is operator-mutable), and a statement is not bound to any session
value, so equivocation is neither detectable nor slashable. Bonds as planned punish double-signing
only and do nothing against link 1. Rows die (three did on genesis day), each death moves the live
set closer to the quorum floor, and every repair is a new category that every consumer must
recompile against.

Mitigations: diversity requirements for the table (operator, jurisdiction, hosting ASN, build);
reproducible, independently compiled binaries; keys in a TPM or signing sidecar; bind statements to
a notary nonce or transcript hash (statement-format change) so equivocation becomes provable; a
published succession rule now, and a successor-category pointer settable by 9 of 13 later.

### 7. tlsn is a shared alpha root of trust without a trust dividend

Decision D8 made provers keyless and permissionless, so a notary can be its own prover and the
chain sees only the notary's signature. That is the trust model of a notary fetching the exchange
directly with certificate validation; tlsn adds routing around geo-blocks and the ability for
third parties to drive sessions, not trust. What it also adds is one alpha dependency shared by
all thirteen rows, the stall surface of link 3, and about 43 MB per MPC session as an
amplification vector. A verifier bug that lets a prover equivocate on plaintext is a zero-key
forgery of every row.

Mitigations: heterogeneous rows (direct fetch, MPC, proxy; later a TEE row) so that no single
implementation covers four rows; optional cross-check of a direct fetch against the revealed
transcript before signing (refusing is not choosing).

### 8. Fees, reserve and replay

* The cap of 5,000 sats bounds the fee at about 2 sat/B (k = 7) unless a builder adds a top-up
  input; with one, any fee is possible, so the plan's "re-genesis needed above 1.7 sat/B" is wrong.
  A mempool filled at 2 sat/B stalls every unfunded update (BCH has no replace-by-fee).
* Any builder may spend the full 5,000 per update instead of size + 1. Competitive builders will.
  Outflow rises from about 0.05 to 0.072 BCH per day. Bounded, not dangerous.
* Notaries serve every past statement forever. After a stall of N minutes anyone can replay N
  historical updates, each spending up to 5,000 sats, before the oracle reaches the present.

### 9. Data quality the median does not fix

The notary signs the pinned "last" field with no check of the exchange's own trade timestamp or
spread. Genesis day showed three rows serving a month-old price, a six-hour-old trade and a
one-trade-per-day market, all as genuine statements. Seven of thirteen rows quote a stablecoin as
if it were a dollar. Mitigations are registry and notary policy, not consensus: prefer mid
`(bid + ask) / 2` where offered, refuse to sign when the exchange timestamp is older than a bound
or the spread is wider than a bound, publish the quote mix and terminator per row.

## What held up

Signature binding (tag, VM-order category, raw row byte, table source byte, seq, price); row
bounds (a row ≥ 13 fails the table slice, a 0x80 row cannot duplicate row 0); tie accounting
yields a unique median value; capability pins on head and Tickers; exactly three outputs and zero
fungible amount; no second minting NFT can ever exist; k = 13 uses 46 % of the op-cost budget with a
1,822-B unlocking script. Deterministic RFC 6979 nonces, cross-checked against libauth vectors.
In both notary modes the TLS peer is authenticated against the Mozilla roots with a hostname
check; proxy mode derives keys blind in tlsn and the notary dials the exchange itself; SNI, Host
header and request target (including the query string) all pin to the registry entry; only the
first response and its first body are parsed; future minutes and transcript replay are refused;
the price parser rejects exponents, signs and separators and cannot overflow.

## Minor items

* `req.target.eq_ignore_ascii_case(&absolute)`: the absolute-form target match is
  case-insensitive; drop the branch or make it exact.
* Proxy mode applies no transcript size bound (only MPC checks `max_sent`/`max_recv`); the
  `issued` map and `statements.jsonl` grow without bound and `/v1/latest` is linear in them.
* Hello is read one byte at a time with a per-byte 10 s timeout: a dribbling client holds a task
  for about 38 minutes.
* A price with the sign bit set counts as "lower"; price 0 with negative-zero bytes is writable.
  Cosmetic as long as notaries are honest; harmless otherwise given link 1.
* The Ticker output is 87 B, not the 88 B in the Oracle.cash comment; 708 sats remains correct.
* Public wording to fix: "Thirteen independent notaries", "seven of thirteen", "six liars still
  leave the result inside the honest range", "nobody chooses a number".

## Suggested order of work

1. Words: publish the real thresholds (keys to forge, rows to stall, who selects what).
2. Notary code: session deadline, lock on success, re-check the window at signing, caps.
3. Covenants for the next genesis: `k ≥ 11` or `k` in the commit; `tx.time` bound on `seq`;
   time-keyed burning `sweep()`; decide Ticker inputs in `update`.
4. Table: terminator and jurisdiction diversity; more USD rows; publish the mix.
5. Consumers: a two-phase reference consumer instead of `PriceGated`.
6. Economics and governance: statement binding for equivocation proofs, a succession rule, and
   some fee that reaches notaries; without it the security budget of the table is zero.
